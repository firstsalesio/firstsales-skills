# Campaigns, testimonials, blocked domains, sequences

Campaigns send multi-step email sequences to contacts from lists. Read state before you change it, and re-read it after.

## Common tasks

```bash
firstsales campaigns list --org org_123 --workspace ws_123 --json
firstsales campaigns get --campaign camp_123 --org org_123 --workspace ws_123 --json
firstsales campaigns progress --campaign camp_123 --org org_123 --workspace ws_123 --json
firstsales campaigns analytics --campaign camp_123 --org org_123 --workspace ws_123 --json
firstsales campaigns leads --campaign camp_123 --org org_123 --workspace ws_123 --json
```

## Launching (confirm with the user first)

Launch is a three-step flow. Never skip a step.

1. `firstsales campaigns readiness --campaign camp_123`: returns `version`, `savedVersionId` and `items`. Any item that is not `Passed` and has `blocks.launch` stops the launch. Fix those first.
2. `firstsales campaigns prepare-launch --campaign camp_123 --data '{"savedVersionId":"<savedVersionId>","readinessVersion":"<version>"}'`. Add `"testOverride":true` only if the user agrees to launch without a sent test email. It returns a `confirmation` object: sender ids, how many people get email, send window, credit estimate and a `consequence` sentence. Show that to the user.
3. On a clear yes, write `launch.json` with `savedVersionId`, `readinessVersion`, the `confirmation` object exactly as returned, and a new `idempotencyKey`. Then run `firstsales campaigns start --campaign camp_123 --data-file launch.json`.

Errors from `prepare-launch`:

- `STALE_READINESS` (409): the campaign changed or a blocker came back. Run `readiness` again and start over.
- `TEST_OVERRIDE_REQUIRED` (409): no test email was sent. Send one, or ask the user before passing `testOverride`.
- `ENTITLEMENT_CHANGED` (409): billing needs attention. See billing-usage.md.

Do not edit the `confirmation` object. `start` refuses it if any field differs.

Test email: `prepare-test-email` takes `connectorId`, `savedCampaignVersion` and `readinessVersion`, plus an optional `recipientMemberId` (a workspace member). Then `send-test-email` with the same fields, the returned `confirmation` and an `idempotencyKey`. Test emails go to workspace members, never to contacts.

`pause` stops new sends right away. `resume` restarts sending to real people, so it needs a yes like `start`.

## Workflow targets

```bash
firstsales campaigns workflow get camp_123 --org org_123 --workspace ws_123 --json
firstsales campaigns workflow update camp_123 --include-list list_a --sender conn_123 --dry-run --org org_123 --workspace ws_123
```

`workflow update` sends one PATCH with only the ids you pass (`includeListIds`, `senderConnectorIds`); repeat a flag for several ids. `workflow-update` (PUT) replaces the whole workflow from `--data`; prefer the PATCH form.

## Blocked domains

A blocked domain also blocks its subdomains. `add` needs `--idempotency-key` (the CLI never makes one up). Add `--campaign <id>` to manage one campaign's own list; a campaign cannot lift a workspace block.

```bash
firstsales blocked-domains add example.com --idempotency-key block-001 --org org_123 --workspace ws_123
```

## Testimonials and sequences

`testimonials list|add|update` need `--campaign`; `update` also needs `--testimonial`. `sequences` manages the reusable sequence library (`--template` names one entry).

## Edge cases

- `start` returns 409 when the campaign is already running or the version is stale.
- Analytics lag a few minutes behind sends.
- Weekends may show zero sends when the campaign only sends on weekdays; check the schedule before calling it a bug.
